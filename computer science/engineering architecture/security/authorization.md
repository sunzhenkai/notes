# 授权（Authorization）

授权（AuthZ）判断一个已经识别的主体能否在特定上下文中对某项资源执行某个动作。授权不是登录完成后的单次步骤，而是每次访问受保护资源时都要做出的安全决策。

## 决策要素

一次授权决策通常包含：

| 要素 | 示例 |
|------|------|
| 主体（Subject） | 用户、服务账号、设备；所属租户、角色、组 |
| 动作（Action） | `document:read`、`order:refund`、`user:disable` |
| 资源（Resource） | 文档、订单、账号；所有者、租户、敏感级别 |
| 上下文（Context） | 时间、网络、设备状态、认证强度、请求来源 |
| 策略（Policy） | 角色权限、属性规则、关系或显式访问列表 |

可以把接口统一抽象为：

```text
authorize(subject, action, resource, context) -> allow | deny
```

授权使用的主体和租户信息必须来自经过验证的认证上下文或可信的服务端数据。资源 ID、角色、组织 ID 等请求参数都属于不可信输入。

## 策略与执行架构

大型系统常把授权划分为以下职责：

- **PAP（Policy Administration Point）**：创建、审批和发布策略。
- **PDP（Policy Decision Point）**：根据输入和策略计算允许或拒绝。
- **PIP（Policy Information Point）**：提供主体、资源和环境属性。
- **PEP（Policy Enforcement Point）**：在 API、网关或数据层执行决策。

```text
请求 → PEP 提取可信身份和目标资源 → PDP 读取策略与属性 → 返回决策 → PEP 执行并审计
```

策略可以集中管理，但执行点必须覆盖所有入口。网关适合做粗粒度校验，服务仍需执行对象级、字段级和业务状态相关的细粒度授权，不能假设“通过网关就已经安全”。

## 常见授权模型

| 模型 | 核心思路 | 适合场景 | 局限 |
|------|----------|----------|------|
| ACL | 在资源上列出主体及其权限 | 文件共享、少量资源的显式授权 | 大规模管理和审计困难 |
| RBAC | 用户获得角色，角色聚合权限 | 组织岗位稳定、权限结构清晰的后台系统 | 容易出现角色爆炸，难表达资源关系和动态条件 |
| ABAC | 根据主体、资源、动作和环境属性计算 | 多租户、合规规则、上下文相关策略 | 策略复杂，属性质量和可解释性要求高 |
| ReBAC | 根据主体与资源之间的关系授权 | 协作文档、社交关系、组织层级 | 关系图查询、缓存和一致性更复杂 |
| Capability | 持有不可伪造的能力凭据即可执行特定操作 | 预签名 URL、受限委托、临时分享 | 凭据转发和撤销需要专门设计 |

实际系统经常组合多种模型。例如先用 RBAC 判断用户是否具备 `document:read` 权限，再用 ABAC 校验租户和文档状态，最后用 ReBAC 判断用户是否为所有者或协作者。

## 权限设计

### 权限、角色和策略分离

- **权限（Permission）**描述原子动作，例如 `invoice:read`、`invoice:approve`。
- **角色（Role）**是权限集合，例如“财务审核员”。角色不应直接写死在每个业务判断中。
- **策略（Policy）**把权限与资源属性、关系和上下文组合成最终规则。

推荐使用稳定、可审计的权限名称，让“角色 → 权限”的映射可配置。业务代码检查权限或策略，不要散落 `if role == "admin"`。超级管理员也应有明确作用域、短时提权和完整审计，而不是无条件绕过所有检查。

### 默认拒绝与显式允许

```text
allow when
  subject.tenant_id == resource.tenant_id
  and subject has "document:read"
  and (
    resource.visibility == "tenant"
    or resource.owner_id == subject.id
    or subject has relation "viewer" to resource
  )
otherwise deny
```

拒绝应是默认结果。多个策略组合时要明确优先级和冲突规则，避免一个宽泛的允许条件覆盖更具体的拒绝条件。

### 最小权限和职责分离

- 权限限定资源、租户、环境和有效期，避免无边界的通配符。
- 对付款创建与审批、权限申请与批准等高风险操作实施职责分离。
- 临时提权应要求增强认证、理由、审批或工单，并自动到期。
- 定期回收闲置账号、孤儿权限和不再使用的角色绑定。

## API 授权

### 每个对象都要校验

仅校验“是否登录”或“是否拥有某个接口权限”仍可能产生对象级授权缺陷（BOLA / IDOR）。服务必须加载目标资源的安全属性并验证访问者是否有权操作该具体对象。

```pseudo
identity = require_authenticated_identity(request)
order = orders.get(request.path.order_id)

if order == null:
    return 404

if !authorize(identity, "order:refund", order, request.context):
    return 403

refund(order)
```

列表和搜索接口也要把授权条件下推到查询中，不能先返回所有数据再依赖前端隐藏。批量操作需要逐项校验，或证明整个集合都在相同的授权边界内。

### 功能级与字段级授权

- **功能级**：普通用户不能调用管理员接口，即使知道 URL。
- **对象级**：用户只能读取或修改被授权的具体资源。
- **字段级**：允许修改个人资料不等于允许修改 `role`、`tenant_id`、余额等敏感字段。

请求 DTO 应采用允许列表，只接收当前操作可修改的字段；响应也要按权限过滤敏感字段，防止过度数据暴露。

### HTTP 响应

- 未认证或凭据无效：`401 Unauthorized`。
- 已认证但策略拒绝：通常为 `403 Forbidden`。
- 不希望向无权主体泄露资源存在性：可以一致地返回 `404 Not Found`。

不要在错误响应中泄露策略内部结构、其他租户信息或敏感资源属性；详细拒绝原因可以写入受控审计日志。

## 多租户系统

租户隔离应是一条独立于普通角色权限的硬边界：

1. 从可信认证上下文确定当前租户，不直接采用请求传入的 `tenant_id`。
2. 所有读取、写入、缓存键、消息和对象存储路径都携带并校验租户边界。
3. 查询默认包含租户条件；可使用数据库 Row-Level Security 作为额外防线。
4. 跨租户管理操作使用独立权限、显式目标、短时授权和增强审计。
5. 自动化测试必须包含“同角色、不同租户”的反例。

仅使用全局唯一 ID 不能代替租户授权；攻击者即使猜不到 ID，也不代表系统完成了访问控制。

## OAuth Scope 与业务权限

OAuth Scope 表示客户端被授予的委托范围，是授权决策的一项输入，不等同于业务系统的全部权限。资源服务器仍需检查：

- Token 的签发者、受众、有效期和类型是否正确；
- Scope 是否允许调用当前 API；
- 最终用户或服务主体是否有权访问这个具体资源；
- 租户、所有权、业务状态和上下文条件是否满足。

例如 `orders:read` Scope 允许客户端请求订单读取接口，但不能自动意味着当前用户可以读取所有租户的所有订单。

## 缓存与一致性

授权决策可以缓存，但缓存键至少要区分主体、租户、动作、资源、关键上下文和策略版本。权限回收、成员关系变化或策略发布时应主动失效相关缓存，并为高风险操作使用短 TTL 或实时决策。

当 PDP、属性服务或依赖不可用时，安全敏感操作通常应失败关闭（fail closed）。如果业务确实需要降级放行，必须明确风险边界、允许的只读能力、时限和告警机制。

## 审计与测试

审计事件建议包含：

- 主体、代理主体和租户；
- 动作、资源类型与资源标识；
- 允许或拒绝、命中的策略及版本；
- 时间、来源、请求 ID 和认证强度；
- 提权、委托或模拟登录的理由与审批信息。

授权测试应采用“主体 × 动作 × 资源状态 × 租户”的权限矩阵，并同时覆盖：

- 正向用例：明确允许的操作成功；
- 反向用例：无权限、权限已撤销、认证过期时失败；
- 横向越权：同级用户访问他人对象失败；
- 纵向越权：普通用户调用管理员功能失败；
- 跨租户越权：相同角色访问其他租户数据失败；
- 批量、导入导出、异步任务和内部接口等非主路径。

## 常见误区

- 只在前端隐藏入口，没有服务端授权。
- 只校验角色，不校验资源所有权、租户和业务状态。
- 把 OAuth Scope、JWT Claim 或难以猜测的资源 ID 当成完整授权。
- 信任客户端提交的 `user_id`、`role` 或 `tenant_id`。
- 在网关做一次粗粒度检查后，内部服务全部放行。
- 权限变更后，会话、Token 或授权缓存长期不失效。
- 存在永久超级管理员、共享服务账号或无法追溯的人工改库。
- 只测试允许路径，没有系统性测试拒绝和越权路径。

## 检查清单

- [ ] 所有受保护入口均默认拒绝，并在服务端执行授权。
- [ ] 主体、动作、资源、上下文和策略边界定义清晰。
- [ ] 对象级、功能级、字段级和多租户授权都有覆盖。
- [ ] 角色只聚合权限，复杂业务条件由可审计策略表达。
- [ ] 权限授予有负责人、理由、作用域、期限和回收机制。
- [ ] 策略变更和权限撤销能及时影响 Token、会话与缓存。
- [ ] 拒绝决策、提权和跨边界操作具有安全审计和告警。
- [ ] 自动化测试包含横向、纵向、跨租户和非主路径越权用例。
